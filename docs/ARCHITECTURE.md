# Architecture

RowBridge is a local single-process application built around four boundaries: ingestion, matching, persistence, and review/export.

## System boundary

```text
browser
  |
  | localhost HTTP
  v
FastAPI + Jinja
  |
  +--> ingestion --------> staged local files
  |
  +--> reconciliation ---> candidate generation ---> scoring/selection
  |                                                  |
  |                                                  v
  +-----------------------------------------------> SQLite
                                                     |
                          +--------------------------+------------------+
                          |                                             |
                          v                                             v
                     review mutations                              CSV / XLSX
```

There is no frontend build system, external queue, cloud database, or required API key.

## Ingestion

`ingestion.py` owns file decoding and structural validation.

It accepts CSV and XLSX input, normalizes the data into `InputTable`, and rejects malformed files before a run is created. Upload reads are capped at the configured size limit plus one byte so oversized requests can be rejected early.

Staged upload filenames are generated by the application rather than taken from user-provided paths. Staging copies are removed after successful run creation, and abandoned stage directories expire automatically.

## Candidate generation

`candidates.py` reduces the number of row pairs that reach the scorer.

The fast path indexes normalized primary values. Supporting indexes can add candidates from secondary text, numeric, and date blocks. A limited fuzzy fallback is used only when normal blocking produces no candidate and the target set is small enough to scan.

The candidate generator also returns diagnostic counts used by tests and available for future observability.

## Scoring and selection

`matching.py` converts the selected mapping into typed rules and scores each candidate.

The matching layer is repeatable and local. It does not call a language model or remote service.

After scoring, candidates are sorted by descending score and then by source row indexes. The selector walks that order and keeps a pair when neither row has already been used. This is deterministic greedy selection, not a global assignment optimizer.

Ambiguity checks use per-source-row competitor indexes so selected pairs do not repeatedly scan the full candidate list.

## Persistence

`storage.py` owns SQLite access.

The database stores:

- run metadata;
- source row payloads;
- current match state;
- algorithmic evidence;
- human review events.

Human actions update the current match state and append a review event. This keeps the current reconciliation view separate from the audit history.

SQLite uses foreign keys, WAL mode, a busy timeout, and normal synchronous mode.

## Web layer

`web.py` handles HTTP input, delegates reconciliation work to the service layer, and renders server-side templates.

The app binds to loopback by default. Trusted host checks and restrictive response headers reduce accidental exposure. Browser Fetch Metadata provides an additional signal for rejecting cross-site mutation requests without making normal local form submission depend on `Origin` behavior.

## Exports

`exports.py` renders the persisted reconciliation state rather than re-running the matcher. Exports therefore include human review decisions already applied to the run.

Spreadsheet formula-like text is escaped before CSV and XLSX output.

## Design choices

### SQLite instead of PostgreSQL

The product is local-first and single-user. SQLite keeps setup small while still providing durable state and transactions.

### Server-rendered HTML instead of a SPA

The workflow is mostly forms, previews, and tables. A separate frontend toolchain would add build and runtime complexity without improving the main workflow.

### Typed rules instead of embeddings or an LLM

The matching problem benefits from predictable scoring, inspectable evidence, offline operation, and repeatability. Human review handles ambiguity directly.
