# Architecture

RowBridge is deliberately small enough to understand end-to-end. It is a local single-process application built around four boundaries: ingestion, matching, persistence, and review/export.

## System boundary

```text
browser
  |
  | localhost HTTP
  v
FastAPI + Jinja
  |
  +--> ingestion --------> staged local files
  |
  +--> reconciliation ---> candidate generation ---> scoring/resolution
  |                                                  |
  |                                                  v
  +-----------------------------------------------> SQLite
                                                     |
                          +--------------------------+------------------+
                          |                                             |
                          v                                             v
                     review mutations                              CSV / XLSX
```

There is no frontend build system, external queue, cloud database, or required API key.

## Ingestion

`ingestion.py` owns file decoding and structural validation.

It accepts CSV and XLSX input, normalizes the data into `CsvTable`, and rejects malformed files before a run is created. Upload reads are bounded by the configured size limit plus one byte, so an oversized request is not intentionally consumed into application memory in full before rejection.

Staged upload filenames are generated by the application rather than derived from user-provided paths. Staging copies are removed after successful run creation; abandoned stage directories expire automatically.

## Candidate generation

`candidates.py` reduces the number of row pairs that reach the scorer.

The fast path indexes normalized primary values. Supporting indexes can add candidates from secondary text, numeric, and date blocks. A bounded fuzzy fallback is used only when normal blocking produces no candidate and the target set is small enough to scan safely.

The candidate generator returns both candidate pairs and diagnostic counts, which are useful for tests and future observability.

## Scoring and resolution

`matching.py` converts the selected mapping into typed rules and scores each candidate.

The matching layer is deterministic. It does not call a language model or remote service.

After scoring, a global one-to-one resolver selects non-conflicting pairs. Ambiguity checks use per-source-row competitor indexes so selected pairs do not repeatedly scan the full candidate list.

## Persistence

`storage.py` owns SQLite access.

The database stores:

- run metadata;
- source row payloads;
- current match state;
- algorithmic evidence;
- human review events.

Human actions are modeled as state mutations plus append-only review history. That separation lets the current reconciliation table evolve while preserving an audit record of reviewer decisions.

SQLite uses foreign keys, WAL mode, a busy timeout, and normal synchronous mode.

## Web layer

`web.py` is intentionally thin. It validates form inputs, delegates reconciliation work to the service layer, and renders server-side templates.

The app binds to loopback by default. Trusted host checks and restrictive response headers reduce accidental exposure. Browser Fetch Metadata is used as an additional signal for rejecting cross-site mutation requests without making normal local form submission depend on fragile `Origin` behavior.

## Exports

`exports.py` renders the current persisted reconciliation state rather than re-running the matcher. This keeps exports aligned with human review decisions.

Spreadsheet formula-like text is escaped before CSV/XLSX output.

## Why these choices

### SQLite instead of PostgreSQL

The product is local-first and single-user. SQLite reduces operational complexity and makes the application portable while still providing durable state and transactions.

### Server-rendered HTML instead of a SPA

The application workflow is form- and table-oriented. A separate frontend toolchain would add maintenance cost without improving the core engineering signal or user workflow.

### Deterministic rules instead of embeddings or an LLM

The core problem benefits from predictable scoring, inspectable evidence, offline operation, and repeatability. Human review handles ambiguity explicitly rather than hiding it behind a non-deterministic model.
